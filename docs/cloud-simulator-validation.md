# Cloud Simulator validation

The signed-in cloud UI tests use `-cloud-signed-in-fixtures` in a DEBUG build. The real client serializes requests into an in-process URLProtocol transport. It intercepts all requests from that client, accepts only `https://chronograph-ui.invalid/chronograph`, and rejects other origins. Secure storage is in memory, cloud preferences use a fresh private defaults suite, and source calendar reads use synthetic events. These tests do not authenticate with Apple, reach the deployed API, read personal calendars, or write meeting events into EventKit.

## Swipe unsubscribe crash regression (2026-10-29)

A pre-fix Simulator run reproduced the reported `NSInternalInconsistencyException`: `Invalid update: invalid number of items in section 0`. The collection had seven items before and after opening removal review, while SwiftUI's destructive swipe action declared one deletion. The application stack passed through `destructiveAction`, `performBatchUpdates` and UICollectionView's item-count assertion. The baseline result and its crash diagnostics are retained at `/private/tmp/ChronoGraph-unsubscribe-crash-baseline.xcresult`.

The selector and received-calendar management now use ordinary red-tinted swipe buttons to open review, with full-swipe invocation disabled. Only the final confirmation performs unsubscribe. The selector also represents owner headings and calendars as individual rows with distinct, stable identity namespaces, so removing an owner's final calendar does not change the row count emitted by a surviving ForEach element. Management retains its normal owner Sections. Both entry points continue to use the same confirmation and receiver-scoped API.

The final run passed 204 logic tests in 23 suites and seven UI journeys on iPhone 17 Pro/iOS 26.5. The four new gesture journeys cover picker swipe cancellation/reopening, removal of each owner's last calendar and the final subscription, long-press singleton removal and foreground refresh, full swipe without automatic review, and management-page swipes through the empty state. Existing inline confirmation, failure/retry and owned-cloud ordering/display checks also passed. Full-swipe and final-empty-state screenshots were visually checked. Twenty-two explicitly opt-in native/live integration tests remained skipped. Debug and Release Simulator builds passed. Results are retained at `/private/tmp/ChronoGraph-unsubscribe-crash-validation.xcresult`; the Release build log is `/private/tmp/ChronoGraph-unsubscribe-crash-release.log`. This client-only fix does not require another backend deployment; installation and validation on the user's physical phone remain outside these Simulator checks.

## Display sources and received-calendar unsubscribe (2026-10-29)

The View menu no longer duplicates shared-calendar creation; Share → Share a Calendar retains both creation channels and resumes existing drafts. Schedule Overview's display selector leads with owned cloud sharing copies and calendars received from other accounts, grouped by owner identity. Provider calendars follow, grouped by actual EventKit source identity so equal account titles remain separate. App-maintained copies, subscriptions and read-only calendars have attribute labels. Provider attributes do not establish ownership or who shared a calendar; those relationships remain managed by that service or the system Calendar app. The existing iCloud shared-view browser continues to select local viewing candidates without publishing.

Owned cloud selections read the server's published snapshot, with the same coverage, per-event and field limits as other cloud display data. Existing selection storage remains compatible; owned copies are not silently selected beside local originals. Loading and metadata failures remain explicit in the selector, with retry/pull-to-refresh and retained cached rows. Both catalog halves commit together, and session/token changes invalidate old catalog/event results.

Received subscriptions can be removed from the selector's swipe/context menu or received-calendar management through one shared confirmation page. Success clears the received permission, display selection and related search results; earlier metadata, event and availability reads cannot restore them. Failure preserves the source and selection for an explicit retry. The backend's receiver-scoped, idempotent DELETE preserves owner data, other viewers, independent public feeds and confirmed meeting history/tasks. Owned sources cannot be removed through the recipient route. The original consumed pairing link remains consumed; the owner must provide a fresh valid link to rejoin.

UI coverage includes both old and owned cloud projections, permission downgrade, incomplete coverage, unsubscribe cancellation/success/failure/retry, no resurrection after refresh, metadata failure versus an empty catalog, retained viewing context, removed duplicate creation and preserved creation/draft consent. Source-group and unsubscribe-review screenshots were visually checked. Debug test builds and the final Release Simulator build passed; native provider behavior and installation on a physical phone were outside these synthetic checks.

Release `20261029-receiver-unsubscribe` was deployed after a verified private backup. The API alone was replaced; the database/nginx containers and migration head `a64c31e8f902` were retained. Runtime source/image hashes, API health and HTTPS liveness/readiness passed. Three disposable accounts verified real unsubscribe, other viewer/owner/feed preservation, confirmed meeting/task preservation, rejected reuse of consumed links and explicit rejoining with fresh links. ## Multiple-calendar configurations and event rules (2026-10-29)

The cloud editor now follows the same configuration semantics as calendar-account sharing: a named output selects multiple local calendars, dates, default content, and occurrence/series exceptions. Source selection, local event preview and final review are separate pages. The channels use the same event-rule and original-event components, and the same event list, source rows, date controls, content choices and scope summary. Local original titles are shown only while editing; the final review uses the actual outgoing projection. Excluding an event removes it from the uploaded snapshot and common-time calculation through that configuration. The same local calendar can participate in separate configurations with independent rules.

Legacy single-calendar bindings keep their original range, content level and wire event IDs. New event IDs include calendar and configuration identity, preventing equal provider identifiers from merging different calendars. Alias resolution and occurrence/series precedence reuse `SharedCalendarState`; persisted configurations contain identity/rule metadata without original event text. Every selected source must be read successfully before replacing a complete snapshot, and field/count/date limits are checked during review. Confirmation sends the frozen, session-bound review; configuration revisions, source generation and rolling-day boundaries must still match. Failed publication preserves the entire pending configuration, including its creation UUID, and the UI offers a recovery entry. Opening or cancelling edits does not upload.

The source's upload ceiling is derived from the default and individual rules; each included event carries its own `visibility`. The server stores and enforces the minimum of event visibility, source ceiling and recipient permission for JSON and ICS, and the receiving app applies event/recipient limits again. Excluded events are omitted before upload. The additive `a64c31e8f902` migration backfills historical events with their preceding source level. Older clients can omit visibility, and pre-upgrade snapshot checksums remain retryable without an idempotency conflict.

Client validation passed 185 logic tests in 21 suites and 14 distinct UI journeys across focused reruns. Coverage includes the exact mixed-rule snapshot from two calendars with overlapping provider IDs, single-upload creation, persisted occurrence rules, cancellation without creation, consent reset after source/date/content changes, existing configuration edits, pause/resume and deletion, iCloud event-rule editing and fast link sending, invitation responses/finalization, and the largest accessibility text category. Initial fixture-date, inline-picker identifier and toolbar-wrapper metadata failures remain in the result bundles; the corrected cases passed their focused reruns. Creation, occurrence-override, final-review and large-text consent screenshots were visually checked for wrapping, clipping and reachable actions. Debug test builds and the final Release Simulator build passed. Native provider propagation and installation on a physical phone were not part of these synthetic UI checks.

The final two-case rerun completed with zero failures. Its optional `simctl diagnose` collector stalled after test completion and was stopped separately; Xcode then finalized the result bundle and exited successfully. The saved bundle reports `Passed`, two passed tests and zero failures/skips. Logs and screenshots were preserved, and the dedicated Simulator was removed.

The backend passed 96 tests and a separate PostgreSQL migration/locking/permission check. A verified private database backup preceded deployment of `20261029-multi-source-rules`; only the ChronoGraph API container was replaced. The database and shared nginx containers retained their identities. Production HTTPS liveness/readiness and migration-head checks passed. Two disposable accounts exercised mixed event levels, full/opaque feeds, common-time search, unchanged legacy snapshot retry, and permission reduction followed by an increase. Both accounts and their session/source/grant records were removed, and only the two new registration invitations were revoked. Existing accounts and invitations were not modified. Deployment evidence remains in the release directory's `deployment-status.json`, `deployment.log` and `live-smoke.log`.

## Unified sharing and invitation inbox (2026-10-28)

Home → Share → Share Calendar opens one hub containing existing calendar-account and ChronoGraph cloud sources, with a new-calendar action for each channel. An already selected iCloud shared calendar retains direct sending of its saved subscription link; Other Sharing Methods opens the hub. Saved-link sending and cloud sharing-method actions appear before the detailed scope summary. The two channels reuse source rows, rolling/fixed date controls, content choices and scope summaries, while retaining their own eligibility and explicit transfer consent. Opening or cancelling a draft does not publish changes or create access.

Cloud creation and source management use the same scope editor. The initial range can come from the home view, and confirmed ranges persist with the local binding; existing bindings retain the past-seven/next-90-day default. The server limit remains 180 elapsed days. Source/date/field changes reset consent. A confirmed upload continues to that source's sharing methods, without uploading again when the user opens sharing or cancels an edit. Pending scope and creation UUIDs are persisted before network mutations, so retries recover lost responses without reverting to wider fields or dates or duplicating a source. New links are blocked while an update is pending. Link creation also checks that the reviewed fields, generation and coverage still match the current source, requiring another review if they changed.

The counted home invitation entry covers guests awaiting a response and organizers whose future proposal has all participants' acceptance and awaits final confirmation. Inbox, cloud workspace and detail pages reuse the same groups and refresh status. Invitation reads run independently of calendar uploads, upload throttling and unrelated busy state. Failed reads preserve cached records with explicit error/retry; non-authentication invitation failures do not stop a valid calendar upload. Account/server changes and newer reads reject old results, and accepted/finalized mutations cannot be overwritten by an older in-flight read. Expired proposals cannot be accepted or finalized from the detail page.

The final logic run passed 168 tests, including 24 source-management and 17 invitation tests. Six distinct `UnifiedSharingUITests` journeys cover both hub channels and actual system-link payloads, the existing iCloud fast-send path, consent invalidation/cancellation, a single confirmed cloud upload with a persisted three-day range, guest acceptance, and organizer final confirmation. The cloud creation fixture rejects link creation unless exactly one snapshot was uploaded. Focused reruns retain the initial test-locator/system-popover dismissal failures in their result bundles. Eight backend snapshot/sharing tests passed. Debug testing and the final Release Simulator build passed. These synthetic checks do not verify phone delivery, push notifications, iCloud propagation or background execution.

## Receiver sharing workflow (2026-10-28)

Received cloud calendars can be selected from the home screen's View menu → Choose Calendars to Display. The selector combines local calendar groups with a separate received-cloud section and links directly to received-calendar management. Selections are stored per server/account on this device; received event contents stay in memory. Schedule Overview merges selected sources, labels each cloud row with its owner/source, and follows the home date range and display privacy. The shared calendar editor continues to use local source calendars.

The client reapplies opaque/partial/full grants before rendering, so choosing Full locally cannot restore excluded fields. Details are read-only and close when their current projection disappears or changes. Logout/account changes clear received rows. Coverage gaps, expired snapshots and read failures have explicit source status; unknown dates do not appear as an empty calendar. Pull-to-refresh and foreground entry refresh cloud metadata and events. Image export uses the same projected fields and preserves incomplete-data notices. Browsing cloud calendars does not require EventKit access; the home screen still offers the local authorization/settings action.

`CloudSharedScheduleTests` covers source-scoped event IDs, field permission limits, partial coverage, stale sources, failures, and suspended requests across dates, permissions and accounts. `CloudSharedScheduleUITests` uses the `cloud-home*` synthetic fixture scenarios for mixed local/received display, date changes, retry/logout, revoked access and foreground permission downgrade while full details are open. ## Calendar snapshot timezone regression (2026-10-28)

The original fixtures used IANA zones and missed Foundation's fixed-offset names (`GMT+0800`, `GMT+0530`). The event API now accepts bounded Foundation offsets and uses the same resolver for all-day ICS dates. The production user confirmed synchronization recovered after the server update; no account recreation or source deletion was needed.

`CloudEventKitIntegrationTests/testNativeReaderSerializesFixedOffsetZonesAndAllDayDates` creates a dedicated local calendar on a disposable Simulator, reads real EventKit values, projects only opaque fields and attaches `native-fixed-offset-snapshot.json`. That exact Swift-generated body was accepted by the production API in a temporary account. Readback, idempotent retry, all-day ICS dates and preservation of prior coverage after an invalid zone all passed; the account and its invite were cleaned up.

The regression run passed 84 backend tests, 120 Simulator logic/Keychain tests and the native EventKit case, with no skips. Debug and Release builds passed. Wire dates retain six fractional digits to match server microsecond precision; intervals that collapse at that precision are rejected locally. Structured 422 feedback exposes only known field labels and event indices, never rejected event content or credentials.

## Password accounts

The default Personal Team build supports username/password sessions while `CHRONOGRAPH_APPLE_SIGN_IN=NO`. Apple-only sessions remain dormant. `CloudPasswordAuthenticationTests` checks the server/client username and password boundaries, account-scoped device IDs and backward-compatible provider decoding. The native Keychain suite uses random test keys on an explicitly opted-in Simulator and removes them afterward.

`CloudPasswordAuthenticationUITests` uses `-cloud-password-fixtures`, with `password-fresh` or `password-restored`. Restored sessions pass through the production decoding/restoration path with an isolated memory store. Cases cover invalid-invite retry, wrong-password retry, login/logout/relogin, password change with a wrong current password, and calendar upload remaining disabled until separate consent. Set `CHRONOGRAPH_AUTH_TEXT_SIZE=UICTContentSizeCategoryAccessibilityXXXL` and `CHRONOGRAPH_AUTH_STYLE=Dark` to repeat the same paths on iPad with large text.

The iOS 26.1 Simulator can substitute an `Automatic Strong Password cover view text` overlay for new-password input, corrupting injected test text. On an explicitly disposable Simulator, `CHRONOGRAPH_MANUAL_PASSWORD_SIMULATOR=1` prepares manual entry by opening Settings → General → AutoFill & Passwords and disabling password AutoFill on that device. This option never changes a physical device and should not be used with a personal Simulator. Production fields retain Apple's recommended `newPassword` content type; real password-manager generation/fill remains a device acceptance check. See [Apple's input configuration](https://developer.apple.com/documentation/security/enabling-password-autofill-on-a-text-input-view).

The deployed password service was additionally exercised over real HTTPS using three temporary accounts: six mutual calendar grants, three opaque busy snapshots, merged common-time search, participant responses, host confirmation, durable tasks and cancellation. The verification script deleted the synthetic accounts and revoked its invite. This checks server coordination; calendar writes and real-device background delivery remain separate acceptance steps. Registration invitations are local private operator files, excluded from Git and test artifacts.

`CloudSignedInWorkspaceUITests` covers consent and upload privacy, source/account deletion, nickname updates, grants/feed revocation, incoming links, grouped people, candidate invalidation, proposing, responding, confirmation/cancellation, stale data, conflicts, empty results, expired sessions, recoverable server failures, and logout while revocation is delayed or fails. Screenshot attachments are retained in the test result bundle. `CloudDatePresentationTests` verifies declared timezone wall times, date boundaries and daylight-saving transitions.

`CloudWorkspaceMatrixUITests` has three focused presentation journeys: compact screen with the largest accessibility text category, dark guest responses, and landscape candidate/meeting screens. Choose the compact Simulator as the test destination; the tests do not change the Simulator model. The matrix runner accepts these environment overrides:

| Variable | Values/default |
| --- | --- |
| `CHRONOGRAPH_MATRIX_LANGUAGE` | `zh-Hans` by default; also supports `en` |
| `CHRONOGRAPH_MATRIX_LOCALE` | `zh_CN` or `en_US`, inferred from language |
| `CHRONOGRAPH_MATRIX_ORIENTATION` | `portrait`, `landscapeLeft`, `landscapeRight`; otherwise the journey default |
| `CHRONOGRAPH_MATRIX_STYLE` | `Light` or `Dark`; otherwise the journey default |
| `CHRONOGRAPH_MATRIX_TEXT_SIZE` | Apple content-size category, such as `UICTContentSizeCategoryAccessibilityXXXL` |

Presentation tests check reachability and record screenshots. Visual inspection of those screenshots is still required to confirm wrapping, contrast, and truncation. Their presence in this repository does not imply a successful run; retain the actual `.xcresult` when reporting results.

Cloud labels, privacy disclosures, common local errors, and manager notices now use the English/Chinese Cloud table and follow the app's selected language. Some formatted dates and less common server validation feedback still follow system/server formatting. Apple sign-in entitlement/real authentication, production API interoperability, and native calendar projection need separate validation.
