# iCloud 共享日历验收

此清单用于首版发布前的人工验收。自动化测试只使用虚拟事件和模拟存储，不应读取或修改开发者的真实日历。下列涉及写入、公开与删除的步骤，应由测试人员主动在专用测试账户和日历上执行，并记录实际结果，不能因为编译通过就标记完成。

## 环境与构建

- 准备已登录测试 Apple Account、开启 iCloud 日历的 iOS 17+ 真机，以及使用另一账户的订阅设备或桌面日历。避免使用个人或工作数据。
- 分别构建 Debug、Release。检查成品 `ChronoGraph.app/Info.plist` 中的完整访问说明，以及 `UIBackgroundModes` 包含 `fetch`、`BGTaskSchedulerPermittedIdentifiers` 包含 `com.shiyao-zhang.ChronoGraph.shared-calendar-refresh`。检查后台注册使用同一标识。
- 首次授权说明应准确描述读取预览/图片，以及明确确认共享后向所选账户写入副本、由账户服务商同步至云端并按规则持续更新。拒绝授权、仅写入权限和重新授权均不得绕过完整访问要求。
- 应用与两个测试 target 的最低部署版本为 iOS 17。当前 Xcode 27 自带的 Swift Testing 模块以 iOS 17 为最低目标；运行测试仍需安装相应可用模拟器运行时。

## 配置与字段

1. 在测试账户准备两个来源日历。创建普通、全天、跨日、忙闲不同的事件，以及一个含改期和取消例外的重复系列；标题、地点、备注、URL 分别使用容易辨认的测试文字，另加参会者与提醒以检查剥离。
2. 创建两份共享配置：使用重叠来源但不同默认可见性和时间范围。选择的账户应明确为 iCloud；无可用目标或目标不可写时，应停留在可修复的错误状态，不能写入系统默认或本地日历。
3. 审阅并确认配置、完成同步后检查两份专用日历，确认各自范围及字段正确，原始来源未改变。完整只增加地点和备注，不能带入参会者、组织者、提醒、附件或原日程 URL。输出 URL 应仅为包含随机标识的应用标记，不能编码来源 ID 或文字。
4. 验证单次覆盖 > 系列覆盖 > 默认值；“不分享”不生成副本。取消覆盖后恢复继承。重复系列单次改期后，覆盖仍跟随正确的那次日程，其他次数不受影响。
5. 将完整降为缩略、隐藏、不分享，逐次审阅确认并同步，直接检查系统日历中旧的地点、备注、标题是否被清空或对应副本被删除。仅在应用预览里遮罩不算通过。
6. 修改固定范围并审阅确认后，核对结束日按配置包含且结束边界排他；测试午夜、跨日和跨夏令时时区。滚动范围跨天后在下次成功更新时推进，移除已经不属于窗口的受管副本。

7. 单独在一条输出事件上手动添加参会者或组织者，再更新：应用应报告需修复并阻止该次同步，不能显示成功或声称只读字段已被清除。由测试人员在系统日历修复后再重试；已有公开副本在失败期间仍可能存在。

## 同步与恢复

1. 连续更新三次后，数量和目标事件身份保持稳定，不产生重复；修改、删除来源事件以及取消单次重复日程后，目标正确收敛。
2. 所有输出日历均不能选作来源，多份配置不会互相复制；一次镜像写入引发的事件库通知不得持续触发循环。
3. 清空来源选择、删除一个来源日历、撤销访问权限，确认不会回退全选、扩大共享范围或用不完整源结果误删输出。
4. 同步期间审阅并确认新的隐私设置，确认旧任务不会随后恢复更宽松的内容；暂停后不得继续提交新的同步批次。
5. 在写入前后中断进程、模拟保存失败，重新打开后重试：不应重复创建副本；状态不能显示为成功；配置、覆盖和已存在目标能够重新核对。错误和日志不应包含测试事件标题、备注或账户凭据。

   创建目标时特别检查 EventKit 已保存而 SwiftData 尚未记录目标 ID 的中断：恢复应使用原操作的随机临时名称标记找回同一目标，随后改为友好名称；普通同名日历不能被绑定。目标账户不可见时保留状态并阻止删除或重建；旧编辑页的版本落后时应拒绝保存。
6. 从系统日历删除专用目标，回到应用后应提示修复，不能凭同名日历或默认日历自动重新绑定。
7. 暂停、关闭系统共享和删除输出是不同操作。删除前的确认必须说明整份专用日历及手动加入内容都会删除。测试人员确认后才执行删除，其他配置及来源日历应保留。

8. 从已知输出事件上清除标记 URL，再将其设为“不分享”：应用应先以隐藏字段恢复标记再删除。模拟删除失败时只能留下忙闲占位，重试后可清理；不能写回原来的完整详情。

9. 检查共享状态 SwiftData 专用目录的 `isExcludedFromBackup` 为真。在独立测试安装或设备迁移演练中确认配置不会随备份恢复、不会自动接管已有 iCloud 日历；不要为测试删除开发者日历或真实应用资料。

## 主页共享体验

1. 使用底部与可见性、日期、分享并列的视图按钮，在“我的日程”与各个具名共享日历之间切换；“添加共享日程”应直接打开新建流程，不承担通用共享视图切换。四个按钮使用相同的工具栏菜单样式；分享菜单只含图片和日历链接，不含共享规则修改。主页不增加分段栏或配置卡片；日期标题、事件行、空白日期及折叠规则复用同一日程组件。个人查看设置与每份共享日历的本机查看设置分别保留，切换日历时不得串用事件、范围、来源或导出缓存。
2. 两种主页使用统一日期菜单：今天、3 天、7 天、14 天和自定义。快捷项是滚动范围的特例，即过去 0 天、未来 0/2/6/13 天，均包含今天；自定义提供“随今天滚动”和“固定日期”。检查滚动范围包含今天、固定范围首尾两天均包含，并按所选范围的时区处理跨午夜及夏令时。
3. 在共享主页切换日期、可见性或本机来源选择，只改变本机查看，不修改已确认的共享配置，也不触发按这些查看设置发布。重启后恢复本机查看状态；其他共享日历与个人设置应保持不变。“恢复共享预览”应恢复按已确认范围、来源和可见性展示。本机选择“完整详情”应明确标注仅自己可见；按共享规则展示时，隐藏事件的原始标题不能出现在对外投影或辅助功能标签中。
4. 共享主页的状态行应始终可点击，作为修改共享的入口。日期或来源与已确认规则有差异时，点击“本机查看，不影响共享”应仅将当前日期和来源作为候选直接进入审阅，本机“完整详情”权限不得导入，进入审阅本身不得更新共享。日期和来源无差异时，点击状态行进入共享编辑器。已有草稿时先提示选择“合并当前日期与来源并审阅”“继续编辑已有草稿”或“取消”：合并只替换日期与来源，保留其他草稿修改及其原版本；取消保留原草稿。修改名称、默认可见性、日期、来源以及关闭后“保留草稿”，均不得改变已确认配置或目标日历；重新打开应恢复草稿。“放弃草稿”应恢复已确认设置，“继续编辑”应留在表单。检查空来源不会回退全选，不可用来源须明确提示并由用户主动移除，受管输出不得成为共享来源。
5. 从编辑器或主页状态行进入审阅页后，核对目标账户与日历、候选日期、来源、默认可见性，以及预计新增、移除和展示更多/更少详情的数量。返回编辑或取消审阅不发布；必须先阅读目标账户、字段范围、跨账户复制和持续更新说明，主动打开默认关闭的传输同意开关，再点击“确认创建共享日历”或“确认更新共享日历”才提交；仅确认账户身份不能代替同意传输，返回编辑再进入审阅时需重新确认。合并已有草稿后必须展示全部修改，不能只展示新导入的范围。预计数量是基于当前来源的估算，不能当作订阅端实时状态。确认期间不能重复提交或关闭；本地配置已保存但同步失败时，应明确区分“设置已保存”和“共享日历尚未完成更新”。
6. 事件详情默认只读，分别展示“原始日程 · 仅自己可见”和已确认的对外投影。先点击“修改共享可见性”才出现继承、完整、缩略、隐藏及不分享选项；候选预览随选择变化，但仍需审阅、主动同意数据传输和最终确认。检查本次与整个系列的范围明确、单次覆盖优先于系列、关闭时可保留或放弃事件草稿，以及取消或返回审阅前均不写入配置。已排除但仍在确认来源/日期内的事件，可经同样确认恢复共享。
7. 对超出已确认日期或来源的事件显示未共享原因；选择完整详情不得自动扩大日期或来源，也不得直接写入可见性覆盖。用户须进入共享规则编辑，审阅并确认纳入范围后再修改事件。若已确认设置在编辑期间变化，旧事件草稿不得套用新版本继续提交；放弃草稿并返回列表，重新获取事件后再编辑。
8. 普通日历选择首次默认及“全选”排除应用创建的日历，但允许用户手动选择共享副本；之后重开保持手动选择。即使用户手动选过共享副本，新建共享的默认来源也不得包含这些副本。额外检查中英文、深色模式、动态字体及 VoiceOver，以及固定范围原时区和未共享事件详情的时间一致。

交互复用日程列表、详情弹窗、表单和工具栏菜单，参考 Apple 的[列表](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)和[工具栏](https://developer.apple.com/design/human-interface-guidelines/toolbars)规范。主页工具栏用于本机浏览，发布规则统一通过草稿及最终审阅确认修改；背景同步只能读取已确认规则。

## 真机分享、后台与撤回

1. 同一个分享菜单仅提供图片与日历链接入口，不承担共享规则确认。共享日历图片预览默认使用“已确认的共享内容”，不得带入本机新增来源、扩大后的查看范围、仅本机完整详情或未确认草稿。主动选择“当前视图”后，明确显示其中尚未共享的事件数量；检查图片内容与预览一致，切换范围或日历时不复用其他上下文的图片。生成预览、选择图片范围和发送图片均不修改订阅规则。
2. 首次在应用完成本机写入后，前往系统日历找到对应 iCloud 日历，手动打开“公开日历”并复制链接；另测邀请特定 iCloud 用户并关闭编辑权限的路径。应用中的日历分享页展示已确认配置及未确认草稿提示，应明确提醒任何公开链接持有者均可读取并转发、订阅持续更新及历史副本无法追回；首次由用户主动粘贴或输入链接、检查并保存。再次进入时应直接展示已保存地址并提供“发送链接”，无需每次重新复制或导入；需要替换时选择“更换链接”。取消更换应恢复原已保存地址，不能清空它或把未保存的新地址当作有效地址。不得因打开页面而读取剪贴板或发送链接，也不得声称应用已通过 EventKit 生成或取得公开链接。
3. 验证手动链接只接受有效的 `webcal` 或 `https` 地址，拒绝包含账户凭据的地址。正在导入或更换时，未保存、无效或保存失败的新地址不得发送；取消后可以恢复并发送原有效地址。目标缺失或不可核实时不能发送。链接应绑定当前配置及目标日历身份；目标重建后，新目标不能继续发送旧目标的已保存链接，须在系统日历重新共享并保存新链接。应用不验证所填链接是否公开或属于该日历；应用内失效旧链接不等于撤销旧目标的系统共享，测试人员仍需检查旧目标和公开访问状态。
4. 在第二设备订阅，核对事件数量、逐条字段和范围。记录本机写入、iCloud 另一设备可见和订阅方刷新三个时间。状态只证明本机更新；公开订阅端允许按自身策略延迟，不能用固定分钟数作为应用通过条件。
5. 来源变更后返回应用，确认前台尝试按已确认规则更新；本机查看及未确认草稿不能影响后台发布。启用后台刷新，记录系统允许执行时的结果；再关闭后台刷新或长时间不打开应用，确认界面没有固定时间或实时更新承诺。调试触发后台任务可测执行逻辑，不能证明日常调度频率。
6. 暂停后检查已有订阅仍可读取旧内容，界面文案应明确“暂停更新不撤回”。暂停期间确认修改只保存设置，恢复后才发布；点击恢复须先显示目标账户、服务商同步和持续更新提醒，取消后继续暂停，明确确认后才恢复；未确认草稿仍不得发布。撤销日历权限后，旧 iCloud 内容也可能存在，应用应提供系统关闭共享或删除的指引。
7. 在系统日历关闭共享或确认删除专用日历后，检查后续访问行为。记录订阅方仍持有的缓存，确认文档不承诺追回已下载、导出或缓存的数据。
8. 全部结束后由测试人员关闭测试公开链接并清理专用测试日历。首版共享配置只由最初设备维护；第二设备即使能看到 iCloud 输出，也不能据此推断配置、覆盖、本机查看设置或草稿已经同步。
